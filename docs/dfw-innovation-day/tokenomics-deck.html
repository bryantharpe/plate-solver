The reveal

Nobody wrote it.

It was built by a fleet of agents working from written specifications. A dispatcher sizes each unit of work, ephemeral workers take one task each, an integration process opens the pull requests.

Humans touch it in exactly four places: approving what gets built, signing off on the highest-risk paths, handling infrastructure escalations, and cutting releases.

So "can AI write real software" stops being the question — the code is on the previous slide, it works, and it passes parity against an independent reference implementation. The question becomes: what did it cost, and what would make it cost less?

Who authored v1

144 commits, by commit author.

v1 was the mixed era — me, Claude, and early agents. v2 removed the human from the implementation loop entirely.

The natural experiment

We deleted the implementation and built it again from the spec alone.

v1 · Jun 9 – Jul 11 · mixed human + agent v2 · Jul 12 – Jul 21 · fleet, spec-only

The rule: v2 had to be derivable from the specs and the reference oracle alone. We deleted our own architecture notes and task breakdown too — so it couldn't just replay v1's build plan.

The honest caveat: some of this is "the second build of anything is faster." That's real. But v1 had zero CI — v2 can't merge without ten required checks and an independent model review. Less code, less time, more verification.

The decision that moves the bill

Nothing in the fleet asks "which model is best."

It asks: what is the cheapest thing that can do this job — and be caught if it's wrong?

Tier 0 · marginal cost ≈ 0 Deterministic gates
  • fmt · clippy -D warnings
  • tests + coverage floor
  • parity vs Python oracle
  • deny · semver · secrets
Tier 1 · local + cheap cloud Authors & independent judge
  • author seats → kimi-k2.7-code
  • small work → local model
  • large work → cloud relay
  • judge → glm-5.2 (other lineage)
Tier 2 · spend on purpose Frontier + human
  • Opus — adversarial review
  • Opus — process audits
  • human — critical paths
  • human — dissents & releases

1 · Route by size. Work is sized before dispatch. Small goes local — marginal token cost is electricity. Most work is small.

2 · The author never grades its own homework. Kimi writes, GLM reviews. Different lineage. A cheap independent reviewer catches what you'd otherwise pay frontier prices for.

3 · The expensive tier is a budget, not a default. Opus is where judgment genuinely decides the outcome — and nowhere else.

Tier 0

The cheapest reviewer on the team is a compiler.

Before any model reviews anything, twelve mechanized gates run. They cost zero tokens, forever.

We audited one merged change end to end. Twelve green checks. Ten were hygiene. Three carried the actual weight — tests traced 1:1 to spec scenarios, the parity oracle, and the independent review. One of the three had to be run by hand.

Green isn't proof. Knowing which gates are load-bearing is what tells you where model spend is actually buying you something — and where it's buying a second opinion on formatting.

The principle: push verification as far down the cost curve as it will go. Deterministic before probabilistic. Cheap model before expensive model. Model before human.

Take this back to your team

Three moves, none of them about token pricing.

01

Route by size, not by habit.

Classify the work before you dispatch it. Most tasks don't need the frontier model, and the ones that do are identifiable in advance. A router is cheaper than a better model.

02

Verify deterministically first.

Every check a compiler, a linter, a schema, or a test can perform is a check you never pay for again. Find your parity oracle — the external thing that proves the output is right without asking a model.

03

Instrument per unit of delivered work.

Cost per merged change. Cost per resolved ticket. Cost per document processed. If your dashboard shows tokens, you're measuring the input — measure the output.

The whole talk in one line: we did not get cheaper by finding cheaper tokens. We got cheaper by changing where the work runs and who checks it.

Over to the room

Three things we'd like to argue about.

Where are you paying frontier prices for work a small model could do?

What's your parity test — the deterministic check that proves the output is right without asking a model?

Do you know your cost per unit of delivered work? Not your token bill.

Appendix A · Q&A backup

Two failures worth more than the successes.

Runaway context burn

One worker ran 72 minutes and 1,410 commands, consumed 100% of its context window, and produced zero lines of code.

Auto-compaction didn't fire on that seat, so an agent that started reading never stopped. Pure burn, no output.

Fix: an explicit context budget in every task brief. Cost control is a prompt-level control, not just a routing one.

The answer key problem

A worker restored an earlier implementation byte-for-byte in 90 seconds — and every gate approved it.

Cheap and fast and completely wrong as a measurement: it proved nothing about whether the spec was sufficient.

Fix: an anti-recovery clause in the brief, and the reason we deleted our own architecture notes before the rebuild. Recovery can't be prevented — only detected.

Both clauses in every task brief today were bought with a failed run. That's the real lesson for anyone budgeting an agent fleet: your first spend is on learning which failure modes cost money.

Appendix B · Q&A backup

Every merged line traces backward.

The provenance chain
  • human-approved spec change
  • → sized task ("bead")
  • → worker branch
  • → pull request
  • → green Tier-2 CI run
  • → independent judge review
  • → human sign-off if critical path
  • → merge commit

Nothing reaches a protected branch that didn't implement an approved spec, pass every mechanized gate, and get reviewed by an independent reasoner. That chain — not trust in the author — is what makes the output defensible.

What the parity oracle asserts

The vendored Python reference wasn't produced by the code under test, so agreement is external validation, not self-certification:

This is the answer to "how do you trust code no human wrote." You don't trust the author — you make the author's output falsifiable by something it can't influence.
